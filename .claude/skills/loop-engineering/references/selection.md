# Issue の選定と base の決定

## 1. 候補の抽出

1. open な Issue を列挙する。**バックログ全体をまとめた Issue（`{backlog}`）は対象外**
2. 各 Issue の本文から依存のセクションを読む
3. 除外条件（下記）に当たるものを落とす
4. 残りを優先順位で1件に絞る

### 依存セクションの見出しの深さは一定ではない

手で書いた Issue は `## 依存`、Issue Forms（`.github/ISSUE_TEMPLATE/*.yml`）から作った
Issue は `### 依存` になる——Forms は各フィールドを `### <ラベル>` として展開するため。
**同じことが「スコープ外」「受け入れ条件 (DoD)」など他のフィールドにも当てはまる。**
どちらの深さも拾う。

### 依存に Issue 番号が併記されていなければ止まる

```markdown
## 依存
E2-2（#6）, E2-4（#8）
```

**番号をそのまま使う。エピックIDから番号を推測して補わない。**

タイトル接頭辞と突き合わせて補う運用は、**接頭辞が1文字違うだけで依存を見落とし、
「依存が無い」ものとして静かに着手する。** 止まらないまま間違った base で進むので、
失敗が見えない。**補わずに止め、書き手に直してもらう。**

## 2. 除外条件

| 状態 | 判定方法 |
| --- | --- |
| 進行中 | その Issue を `Closes #N` で参照する open な PR がある |
| 停止中 | Issue に停止コメント（`{stop_comment}`）がある |
| 着手不可 | 依存先の Issue が未着手（open かつ対応する PR なし） |
| 対象外 | バックログ Issue、報告／停止用 Issue、明示的にキャンセルされたもの |

**依存先が closed でも「open PR あり」でも着手可能とする。**
依存先の実装が PR として存在していれば、その上にスタックして進められる。

## 3. 優先順位

候補が複数あるなら、この順で1件に絞る。

1. 優先度（タイトルの `[P1]` → `[P2]` → `[P3]`。無い運用なら並び順の先頭）
2. **依存先がすべて closed のもの**（＝ `{default_branch}` ベースで作業できるもの）
   — スタックを不必要に深くしないため
3. Issue 番号の昇順

候補がゼロなら、その理由（全て完了／全て進行中／依存待ち／停止中）を明示して終了する。

### 優先度と依存が矛盾したら止まる

**残っている最優先の Issue が、着手できない下位の Issue に依存している場合、
勝手にどちらかを選ばず停止して報告する。**

優先度順に従うと依存先に着手できず、依存順に従うと優先度を破ることになる。
どちらを取るかは人の判断であり、推測で進めると後戻りが高くつく。

## 4. base の決定

- 依存先に **open な PR がある** → その PR の head ブランチを base にする（スタック）
- 依存先がすべて closed、または依存なし → `{default_branch}`

### 依存先の open PR が2本以上ある場合

**一直線とは「1本が他のすべてを祖先として含む」こと。**
どれがそれに当たるかは目で見て決めず、**候補を1本ずつ全部試す。**

- **1本試して失敗しただけでは並列と言えない。** 一直線（A ⊂ B ⊂ C）でも、
  最も深くない B を候補にすれば失敗する
- **1ペアに祖先関係があるだけでも一直線と言えない。** 3本のうち2本が積まれていて
  3本目が並列、という形がある。これを一直線と誤判定すると3本目の依存が base から落ちる

**どちらの向きの取りこぼしも、全候補を試せば起きない。**

```bash
# scripts/stack-base.sh と同じ判定
deps=(feat/9-jsonl-store feat/12-cli-skeleton)

for candidate in "${deps[@]}"; do
  linear=1
  for dep in "${deps[@]}"; do
    [ "$dep" = "$candidate" ] && continue
    git merge-base --is-ancestor "origin/$dep" "origin/$candidate" || { linear=0; break; }
  done
  [ "$linear" = 1 ] && echo "一直線: base は $candidate" && break
done
# 何も出なければ並列
```

| 形 | 判定 | base |
| --- | --- | --- |
| 一直線 | ある1本が残りすべてを祖先として含む | その1本（全ての依存が入る） |
| **並列** | どの1本を候補にしても、含まれないものが残る | **決められない。着手しない** |

### 並列に分かれている場合

**その Issue は選ばず、優先順位の順で次の候補に進む。** どの base を選んでも、
base 付け替えを義務づけている理由（「子 PR の差分に親の変更が重複して現れ、
レビューが不能になる」）に反する。

| 案 | 却下する理由 |
| --- | --- |
| 片方を base にして他方を取り込む | 差分に他方の実装が丸ごと現れる |
| `{default_branch}` から分岐して両方取り込む | 差分に両方が現れ、担当 Issue の変更が埋もれる |
| 一方を他方のブランチに先に取り込む | 別 PR の内容を書き換えることになる |
| 依存が未解決のまま分岐 | 存在しない API に対して実装・テストを書くことになる |

**飛ばしたことは報告に明示する。** 黙って番号を飛ばすと、次の周が同じ Issue を
また候補に挙げて同じ判断を繰り返す。

**飛ばした先の扱い:**

- 同じ優先度に他の候補がある → **それに進んでよい**（禁じているのは優先度を下げることだけ）
- 飛ばすと**より低い優先度に降りる**ことになる → **停止して報告**
  （優先度を守るか着手を進めるかは人の判断）
- **候補がすべて並列依存で埋まっている** → 進める先が無い。**停止して報告**

## 5. スコープ

選定したら Issue 本文を読む。**その Issue のエピック・タスク・DoD だけがスコープ。**
先の Issue を先取りしない。作業中に見つけた別の問題は、その場で直さず Issue として起票する。

本文が空、方針と矛盾しているなど**着手不能なら、推測で進めず報告する。**
ただし「依存先が未マージ PR なだけ」は着手不能では**ない**。上記のとおり base を決めて進む。
