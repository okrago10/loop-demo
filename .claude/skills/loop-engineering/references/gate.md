# ゲート（着手前の点検）

実装に入る前に、**そもそも着手してよい状態か**を3つ見る。順番に意味がある。

1. 停止フラグ（止められていないか）
2. 未対応レビュー（この周を指摘対応に充てるべきか）
3. スタックの健全性（親のマージへの追従、段数）

## 0. フェイルクローズ

GitHub の照会（`gh` / GitHub API / MCP ツール）が失敗したときは、
**「取得できなかった＝該当0件」として進めてはいけない。**

停止フラグの取得に失敗したのに「halt は無かった」として実装を始めると、
止めたはずのループが動く。**照会に失敗したら、その周は進まず報告する。**

`gh` が使える環境ではスクリプト（`scripts/loop-gate.sh`）で判定できる。
`gh` が無い環境では GitHub の MCP ツールで同じ判定を手で行う——
**判定内容が同じであればよく、スクリプトの有無は本質ではない。**

## 1. 停止フラグ

config の `halt` 方式で見るものが変わる。

### `report-issue` 方式

| 見るもの | 効果 |
| --- | --- |
| `{halt_prefix}` で始まる open Issue | **リポジトリ全体で実装禁止。** 報告のみ |
| `{halt_file}` が存在する | 同上。**空でも halt。** 存在チェックだけで判定する |
| `{report_prefix}` で始まる open Issue の**件数** | 未回答の報告が溜まっていないかの指標 |

未回答レポートの件数は「ユーザーが報告に気づかないまま次の自動実行が走った」状態を
検出するためにある。

| open な報告 | この周 |
| --- | --- |
| 0件 | 通常どおり進む |
| 1件 | ユーザー判断待ちなら実装しない。技術的失敗の再試行なら、同じ Issue をもう一度だけ試みる |
| 2件以上 | 実装しない。**停止 Issue を作ってオートメーション自体を止める**（[stop.md](stop.md)） |

### `stop-comment` 方式

停止は Issue 単位で表現する。`{stop_comment}` で始まるコメントが付いた Issue を
**候補から外す**（リポジトリ全体は止めない）。

ただし、**規約ファイルにループ全体の停止条件があればそれに従う。** 典型的には:

- 2つの Issue で連続して停止した（前提そのものが崩れている可能性が高い）
- 依存の上流にある Issue が停止し、後続が着手できない
- リポジトリの状態が想定と食い違う（`{default_branch}` が想定外に進んでいる等）

## 2. 未対応レビューの優先

**「未対応」の判定は、コメントの新しさで決める。**

対象コメントの作成時刻が **PR の head コミットの時刻より後**で、かつ
`{severity}` に当たる指摘を含んでいるなら未対応。

- `review_style: heading-markers` — 本文が `{review_markers}` の見出しで始まるコメント、
  あるいは Claude Code の帰属フッターを含むコメントを対象にする。
  **投稿者の login では判定しない**（オーナー名義で投稿されることがある）
- `review_style: github-review` — 未解決のレビュースレッド、`CHANGES_REQUESTED` のレビュー

**コードレビューとセキュリティレビューが別コメントに分かれることがある。**
新しい「指摘なし」コメントがあっても、head より新しい指摘が別コメントに残っていれば未対応。

| 状態 | この周の扱い |
| --- | --- |
| 未対応の指摘がある | **その PR の指摘対応だけをする。** 別の Issue には着手しない |
| レビューがまだ来ていない | **止まらない。** 次の Issue に進んでよい（レビュー待ちのまま残す） |
| 最新レビューが指摘なし／指摘より後に commit がある | 対応済み。**未マージのままでも**次の Issue へ |

「未マージ PR が残っている」は着手しない理由に**ならない**。スタックさせて進む。

## 3. スタックの追従と深度

### 親がマージされたら追従する

open PR の base ブランチが `{default_branch}` にマージ済みなら:

1. PR の base を、マージ済みの親の base（多くは `{default_branch}`）に付け替える
2. そのブランチに `{default_branch}` を取り込む
3. push する

**怠ると子 PR の差分に親の変更が重複して現れ、レビューが不能になる。**

コンフリクトの解消はプリフライトフェーズの枠で `{retry_limit}` 回まで。
解けなければ、その PR にコメントを残して停止し、新しい Issue には着手しない。

**この枠を使い切っても、これから着手する Issue の実装フェーズの枠は減らない。**
対象が他の PR であって、着手する Issue の作業ではないため。

### 深度

```
main
 └─ PR#29 (1段)
     └─ PR#30 (2段)
         └─ PR#31 (3段)
             └─ PR#32 (4段)
                 └─ PR#33 (5段)  ← {stack_limit} に達したらこれ以上積まない
```

達していたら新規着手せず、**どの PR をマージすれば進めるか**を書いて停止する。

```
スタックが上限（5段）に達しています。
PR #29 をマージしてから再実行してください。
```
