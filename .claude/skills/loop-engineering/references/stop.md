# リトライ上限と、停止のしかた

ループで最も避けるべきなのは、失敗した作業を延々とリトライし続けてトークンと時間を
浪費することである。**直らないものは、止めて人に渡す。**

## 1. カウンタの規則

**失敗を修正しようとする試行は、フェーズごとに最大 `{retry_limit}` 回（既定2回）。
上限に達したら次の試行に入らず、停止して報告する。**

| フェーズ | 範囲 |
| --- | --- |
| プリフライト | 着手前の点検（**他の** PR のスタック追従・コンフリクト解消） |
| 実装 | 着手から PR 作成まで（PR 作成前の CI 確認を含む） |
| レビュー対応 | PR 作成後、レビュー指摘と CI への対応 |

### なぜ別枠なのか

通算にすると、実装で使い切った時点でレビュー対応に入れなくなり、
**指摘に応えられないまま止まる**ことになる。指摘に応える作業は、実装の失敗の続きではない。

プリフライトを別枠にするのは、対象が**他の PR** であり、これから着手する Issue の
作業ではないため。ここで上限に達した場合は新しい Issue に着手せず、該当 PR に
コメントを残して停止する。

### フェーズ内では通算。数え方を厳密に守る

- カウント対象は「`{verify}` または CI が失敗し、**それを直そうとした回数**」
- **エラーの内容が変わってもカウンタはリセットしない**
- **アプローチを変えたことを理由に数え直さない。**
  「別の方法を試すので新しい試行1回目」は抜け道であり、禁止する
- **レビューが複数回来てもリセットしない**
- 停止の判断は、**残りトークンや時間の余裕とは無関係に**行う

### 数えないもの

- 実装した直後の `{format}`（失敗ではなく手順の一部）
- mutation test で落ちなかった箇所へのテスト追加（検証の失敗ではない）
- **条件を何も変えない同じコマンドの再実行**——これは試行に数えないのではなく、**単に禁止する**

## 2. 事象別の上限

| 事象 | 上限 | 超えた場合 |
| --- | --- | --- |
| テスト・型・lint の失敗を修正する | フェーズごとに `{retry_limit}` 回 | 停止して報告 |
| CI の失敗を修正する | フェーズごとに `{retry_limit}` 回 | 停止して報告 |
| 修正しても**同じエラーが再発する** | 2回連続で即停止 | 進捗が出ていない。それ以上試さない |
| ネットワーク・レジストリ等の**一時的な**失敗 | 2回まで再試行（2秒・4秒待ち） | 停止して報告 |
| **仕様の矛盾、DoD が実現不能と判明** | **0回（即停止）** | 推測で進めず、その場で報告 |

リトライしてよいのは、ネットワーク、パッケージのインストール、push、フレークなテスト、
dev server の起動失敗、レビュー取得の一時的な失敗といった**技術的な失敗**だけ。
**ユーザー判断が要る事柄、スコープの破綻、仕様として落ちるテストはリトライの対象ではない。**

## 3. 停止するときの手順

1. **その時点までの変更をコミットし、作業ブランチを push する（捨てない）**
2. 対象 Issue に、下記テンプレートでコメントを残す
3. **次の Issue に進まない。ループを終了する**

部分的で危険なコミットは push しない。**説明可能な途中状態だけ**を残す。

### テンプレート（`halt: stop-comment` のリポジトリ）

```markdown
## 自動作業を停止しました

**対象**: #<issue番号>
**フェーズ**: プリフライト / 実装 / レビュー対応 のいずれか
**停止理由**: そのフェーズの修正試行が上限（N回）に達したため

### 試行1
- 仮説:
- 変更内容:
- 結果:

### 試行2
- 仮説:
- 変更内容:
- 結果:

### 現在の失敗内容
（エラー出力を原文のまま抜粋）

### 人に判断してほしいこと
（何が分かっていて、何が分からないか。想定される選択肢）

**ブランチ**: <ブランチ名>
**最終コミット**: <SHA>
```

### テンプレート（`halt: report-issue` のリポジトリ）

`{report_prefix} <短い理由> (<何回目>/2)` というタイトルで Issue を作る。
何回目かは、既存の open な報告 Issue 数 + 1。

```markdown
## なぜ止まったか

## ユーザーに決めてほしいこと
-

## 試したこと
-

## 回数
このレポートは未回答シリーズの N/2 回目（3回目は halt）。

## 対象
- バックログ: <参照>
- 着手予定だった issue: #<番号>
```

実行の最終メッセージでも同じ内容を報告する。**新しい機能実装を始めない**
（すでに PR がある指摘対応中なら、判断待ち以外は直してよい）。

## 4. 3回目：オートメーション自体を止める（`report-issue` のみ）

open な報告 Issue が既に2件ある状態で、さらにユーザー未回答のまま実行されたら:

1. `{halt_prefix} 未回答レポートが3回目のため停止` という Issue を作る
2. 可能なら `{halt_file}` を追加する PR を出す（タイトルに `STOP AUTOMATION` を含める）。
   中身は停止理由と、解除手順
3. スケジューラ側を API で無効化できない場合は、最終報告で
   **ダッシュボード上で自動実行をオフにする**よう明記する
4. 以降の実行は停止フラグの確認で即終了する

**目的は、報告に気づかないまま作業が進み続けないようにすること。**

解除は人の作業: 報告 Issue を close → 停止 Issue を close → `{halt_file}` を削除して
マージ → 自動実行を再度有効化。

## 5. ループ全体の停止条件

個別 Issue の上限とは別に、以下のいずれかでループ自体を終了する。

- **2つの Issue で連続して停止した**（前提そのものが崩れている可能性が高い）
- 依存の上流にある Issue が停止し、後続が着手できない
- リポジトリの状態が想定と食い違う（`{default_branch}` が想定外に進んでいる等）

## 6. 判断に迷ったら

**勝手に決めずに Issue か PR にコメントを残して止まる方を選ぶ。**
止まったループは再開できるが、間違った方向に進んだループは巻き戻しが高くつく。
