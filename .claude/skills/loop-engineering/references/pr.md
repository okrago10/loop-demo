# PR の作り方と、証拠の残し方

## 原則：チェックには根拠を添える

チェックを入れるだけでは、**確認したのか確認したつもりなのか区別がつかない。**

各 DoD 項目に、次のどちらかを必ず書く。

- 対応するテストの**ファイル名とテスト名**
- **実際に叩いた出力**（コードブロックに貼る）／**スクリーンショット**

**振る舞いに関する項目は、テスト名だけで済ませず実行出力を貼る。**

これは実際に失敗したことがあるから決めた手順である。不正な入力が受け付けられていることが
自分の実行結果に出ていたのに見落とし、PR 本文には「弾いている」と事実と違う記述をした。
**出力を貼る手順にしておけば、貼るために読み直す機会が必ず1回入る。**

```
$ tock start "打ち間違い" --at 23:59
--at に未来の時刻は指定できません: 23:59（現在は 07:24:05）
$ echo $?
1
```

## 原則：理由付けは書く前にコードで確認する

「〜だから、こうした」という設計理由は、**書く前にコードで裏を取る。**
確認せずに書くと誤りやすいのは、とくにこの3つ。

| 主張の型 | 確認方法 |
| --- | --- |
| 依存の向き（「A が B を参照すると向きが逆になる」） | `import` を見る |
| 既存の実装の挙動（「既に弾いている」「対応済み」） | 実際に叩く |
| 他の Issue の担当範囲（「これは #N の担当」） | #N の本文を読む |

**もっともらしい理屈は、確認しないまま書くと通ってしまう。**
分からない場合は、**理由を書かずに「判断が必要」として残す。**

## 本文の型

```markdown
## 概要
（何をしたか、なぜその方針にしたか）

Closes #<issue番号>

## 受け入れ条件
- [x] <DoD 項目>
      → tests/commands/xxx.test.ts の「...」
- [x] <DoD 項目>
      → 実行結果:
      ```
      $ ...
      ```
- [x] <DoD 項目>
      → <img src="..." width="320">

## mutation test
| 壊した内容 | 落ちたテスト |
| --- | --- |
| ... | N件 |
（実装コードを変更していない周は「ドキュメントのみのため未実施」と理由を書く）

## やらなかったこと
（スコープ外として別 Issue にしたもの。番号をリンクする）

## スタック
- base: `main` または `feat/1-...`（PR #29）
- ※ この PR は #29 のマージ後にレビューしてください（スタックしている場合のみ）

## 依存の追加
（追加した場合のみ。パッケージ名・採用バージョン・その公開日・確認結果）
```

## 作成時の約束

- **タイトルは対象 Issue のタイトルに揃える**
- **最初から open（Ready for review）で作る。** `{draft_pr}` が `never` のリポジトリでは
  作成時に Draft でないことを明示する
- **自分でマージしない。** レビューはマージの前提。CI が green でも同じ
- コミットメッセージは規約ファイルの型に従う。`<type>: <要約>` と、
  **何をしたかではなく、なぜそうしたか**を本文に書く

## 証拠の取り方

| `evidence` | 手順 |
| --- | --- |
| `cli-output` | 実際にコマンドを叩き、出力と終了コードを貼る。**ユーザーの実データに触らない**——データディレクトリを環境変数などで一時ディレクトリに向ける |
| `screenshot` | アプリを起動し、`{screenshot_viewport}` を意識して撮る。画像／動画を成果物として残し、本文に埋め込む |
| `none` | 画面もコマンドも無い変更に限る。代わりに実行した検証コマンドとその出力を貼る |

**画面やコマンドがあるのに証拠が無い PR は出さない。**

## 依存を追加した場合に書くこと

- なぜ必要か（何を自前実装せずに済むのか）
- 実在性・メンテナ人数・利用実績・最終更新日の確認結果
- 採用したバージョンと、その公開日

**基準を満たさないと判断したなら、無理に採用せず Issue にコメントして人の判断を仰ぐ。**
