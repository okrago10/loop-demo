# loop-engineering-status

バックログの現在地を表示する。**読み取り専用。**

このスキルは以下を**一切行わない。**

- ファイルの作成・編集
- コミット・push・ブランチ操作
- Issue や PR の作成・更新・コメント

状態はすべて GitHub から導出する。**ローカルに状態ファイルは持たない。**
リポジトリの状態を変更しない操作のみを行う。

## 0. 設定の読み込み

`.claude/loop-config.md` を読む（無ければ
[loop-engineering の references/config.md](../loop-engineering/references/config.md)
の推定表でフォールバックし、推定した値を出力に明示する）。

**判定の基準は `loop-engineering` と一致させる。** ここに「着手可能」と出た Issue が、
`/loop-engineering` を引数なしで実行したときに着手されるものになる。
ずれると、この表示を見て判断したことが実行時に覆る。

## 状態の導出

| 状態 | 判定方法 |
| --- | --- |
| 完了 | Issue が closed |
| 進行中 | その Issue を `Closes #N` で参照する open な PR がある |
| 指摘が残っている | PR に、head コミットより新しい未対応の指摘がある（`{severity}` / 未解決スレッド / `CHANGES_REQUESTED`） |
| 停止中 | Issue に停止コメント（`{stop_comment}`）がある、または `{report_prefix}` の報告 Issue が open |
| 着手可能 | 上記のいずれでもなく、依存先がすべて closed または open PR あり |
| 依存待ち | 依存先の Issue が未着手（open かつ PR なし） |
| 判定不能 | 依存に Issue 番号が併記されていない（**推測で補わない**） |

依存は各 Issue 本文の依存セクションから読む。**見出しの深さは `## 依存` と `### 依存` の
2種類がある**（Issue Forms は各フィールドを `###` に展開する）。両方拾う。

バックログ全体をまとめた Issue（`{backlog}`）は集計の対象外。

## 収集する情報

1. open / closed の Issue 一覧（番号・タイトル・依存セクション）
2. open な PR 一覧（番号・base ブランチ・head ブランチ・対応する Issue）
3. 各 PR の CI 状態（成功 / 失敗 / 実行中）と、未対応の指摘の有無
4. 停止中の Issue とその理由（停止コメントの「停止理由」行）
5. 停止フラグ（`{halt_prefix}` の open Issue、`{halt_file}` の存在）

**GitHub を照会できなかった項目は、0件と表示しない。「取得できず」と明示する。**

## 出力

```
## バックログ進捗

完了 3 / 26   進行中 2   停止中 1   着手可能 4

## レビュー待ちの PR

  main
   └─ PR #29  Issue #1  [E1-1] プロジェクト初期化        CI ✅  ⚠ 未対応の指摘 2件
       └─ PR #30  Issue #2  [E1-2] Lint / Format の整備   CI ⏳ 実行中

  ※ スタック 2段 / 上限 5段

## 停止中

  Issue #9  [E3-1] 永続化：ストアのインタフェースと JSONL 実装
    理由: 修正試行が上限（2回）に達したため
    ブランチ: feat/9-jsonl-store

## 次の着手候補

  1. Issue #5  [E2-1][P1] Entry の型と生成・検証     依存: なし        base: main
  2. Issue #12 [E4-1][P1] CLI の骨格                 依存: #1(進行中)  base: feat/1-...

## 依存待ち / 判定不能

  Issue #13 [E4-2][P1] start / stop     ← #9 が停止中のため着手できない
  Issue #21 [E5-1][P2] 週次サマリ       ← 依存にエピックIDしかなく番号が引けない
```

## 表示のルール

- **候補の並び順は `loop-engineering` と一致させる**
  （優先度 → 依存が全て closed のものを優先 → Issue 番号昇順）
- 各候補には base ブランチを併記する（`{default_branch}` か、スタックする場合は親のブランチ）
- **依存先の open PR が並列に分かれていて base を決められない候補は、そう明示する。**
  黙って順位に混ぜると、実行時に飛ばされる Issue を「次にやるもの」として見せることになる
- 停止中の Issue が他の Issue の依存先になっている場合は、その影響を明示する
  （ループが進めなくなっている原因を一目で分かるようにするため）
- 該当がないセクションは省略してよい（「停止中」が0件なら表示しない）
- 停止フラグが立っている場合は、**最上部に表示する**（他の情報より先に見せる）

## 最後に

状態に応じて、次に取るべき行動を1〜2行で添える。

- 未対応の指摘が残っている PR がある → 人の判断待ちである可能性が高い旨
- 着手可能な候補がある → `/loop-engineering` で着手できる旨
- スタックが上限に達している → **どの PR をマージすれば進めるか**
- 停止中の Issue が後続をブロックしている → その Issue の判断が必要である旨
- 依存の番号が引けない Issue がある → **書き手が Issue を直す必要がある旨**（推測で補わない）
- すべて完了 → バックログを消化しきったこと
