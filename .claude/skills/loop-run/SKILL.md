# loop-run

バックログの Issue を1件だけ処理する。**1起動 = 1 Issue = 1 PR。**

作業を始める前に必ずリポジトリ直下の `CLAUDE.md` を読むこと。開発規約・検証コマンド・
リトライ上限・禁止事項はすべて `CLAUDE.md` が正であり、このスキルはその上で
「1周をどう回すか」の手順だけを定める。両者が矛盾する場合は `CLAUDE.md` に従い、
矛盾していること自体を報告する。

引数で Issue 番号を指定できる（例: `/loop-run 13`）。省略時は自動選択する。

## 全体の流れ

```
0. 前提の読み込み
1. プリフライト（スタック点検と追従）
2. Issue の選択
3. ブランチの作成（base の決定）
4. 実装（テストを先に書く）
5. npm run check
6. PR の作成
7. CI の待機（上限5分）
8. 報告して終了
```

**どの段階でも、リトライ上限（同一 Issue で修正試行2回）に達したら
`CLAUDE.md` の「失敗時の停止ルール」に従って停止し、報告して終了する。**
次の Issue には進まない。

## 0. 前提の読み込み

- `CLAUDE.md` を読む
- `git fetch origin` で最新化する
- 作業ツリーに未コミットの変更がある場合は、**何も変更せず停止して報告する**
  （前回の作業が中断されている可能性があり、勝手に捨ててはいけない）

## 1. プリフライト：スタックの点検と追従

このリポジトリは PR をスタックさせる運用を取る。着手前に、既存のスタックが
壊れていないかを点検し、必要なら追従させる。

### 1-1. 現状の把握

open な PR を一覧し、それぞれの `base` ブランチと対応する Issue 番号
（本文の `Closes #N`）を取得する。これで現在のスタック構造が分かる。

### 1-2. マージ済みの親への追従

各 open PR について、その `base` ブランチが既に `main` へマージ済みなら、以下を行う。

1. PR の `base` を、マージ済みの親の base（多くの場合 `main`）に付け替える
2. そのブランチに `main` を取り込む（マージ）
3. push する

これを行わないと、子 PR の差分に親の変更が重複して現れ、レビューが不能になる。

**コンフリクトが発生した場合**は解決を試みる。ただしリトライ上限は
`CLAUDE.md` の規定どおり2回。解決できない場合は、その PR にコメントを残して
停止し、新しい Issue には着手しない。

### 1-3. スタック深度の確認

`main` から数えたスタックの段数が **5段** に達している場合は、新規の着手を行わず
停止して報告する。

```
main
 └─ PR#29 (1段)
     └─ PR#30 (2段)
         └─ PR#31 (3段)
             └─ PR#32 (4段)
                 └─ PR#33 (5段)  ← これ以上は積まない
```

報告例:

```
スタックが上限（5段）に達しています。
PR #29 をマージしてから再実行してください。
```

## 2. Issue の選択

引数で Issue 番号が指定されている場合は、その Issue を対象とする（ただし
下記の除外条件に該当する場合は、その旨を報告して停止する）。

自動選択の手順は以下のとおり。

### 2-1. 候補の抽出

1. open な Issue を列挙する。バックログ全体をまとめた Issue（タイトルが
   `[BACKLOG]` で始まるもの）は対象外
2. 各 Issue の本文にある `## 依存` セクションを読む。依存はエピックID
   （`E3-1` 形式）で書かれているため、各 Issue のタイトル接頭辞 `[E3-1]` と
   突き合わせて Issue 番号に解決する

### 2-2. 除外条件

以下に該当する Issue は候補から外す。

| 状態 | 判定方法 |
| --- | --- |
| 進行中 | その Issue を `Closes #N` で参照する open な PR がある |
| 停止中 | Issue に「自動作業を停止しました」というコメントがある |
| 着手不可 | 依存先の Issue が未着手（open かつ対応する PR なし） |

**依存先が「closed」または「open PR あり」なら着手可能とする。**
依存先の実装が PR として存在していれば、その上にスタックして進められるため。

### 2-3. 優先順位

候補が複数ある場合、以下の順で1件に絞る。

1. 優先度（タイトルの `[P1]` → `[P2]` → `[P3]`）
2. 依存先がすべて closed のもの（＝ `main` ベースで作業できるもの）を優先する
   — スタックを不必要に深くしないため
3. Issue 番号の昇順

候補がゼロの場合は、その理由（全て完了・全て進行中・依存待ち・停止中）を
明示して終了する。

## 3. ブランチの作成

### 3-1. base の決定

- 依存先の Issue に **open な PR がある** → その PR のブランチを base にする
  （複数ある場合は、スタックが最も深いものを base にすれば全ての依存を含められる）
- 依存先がすべて closed、または依存なし → `main` を base にする

### 3-2. ブランチ名

`CLAUDE.md` の規約に従う。

```
feat/<issue番号>-<短い説明>     例: feat/13-start-stop-command
docs/<issue番号>-<短い説明>
fix/<issue番号>-<短い説明>
```

base ブランチを最新化してから、そこを起点に作成する。

## 4. 実装

**Issue の受け入れ条件（DoD）を、先にテストへ落としてから実装する。**

1. Issue 本文の DoD のチェック項目を読み、それぞれに対応するテストを書く
2. テストが失敗することを確認する（何も実装していないので当然失敗する）
3. テストが通るように実装する

守ること:

- 担当 Issue の範囲を超えた変更を混ぜない。気づいた別の問題は Issue として起票する
- 依存ライブラリを追加する場合は、`CLAUDE.md` の「依存ライブラリの追加ルール」に
  従う（実在性・メンテナ人数・利用実績・最終更新日の確認、公開から7日以上経過した
  最新版、確認結果を PR 本文に記録）
- 失敗するテストを削除・スキップしない。`any` や `@ts-ignore` で型エラーを黙らせない。
  lint ルールを無効化しない

## 5. 検証

```bash
npm run check
```

これが通らない限り PR を作らない。

失敗した場合の修正は **2回まで**。2回目でも失敗したら3回目に入らず、
`CLAUDE.md` の停止テンプレートで Issue にコメントし、変更を push して終了する。

「アプローチを変えたので新しい試行1回目」という数え直しは禁止。

## 6. PR の作成

コミットして push し、PR を作成する。

- **base**: 3-1 で決定したブランチ
- **タイトル**: 対象 Issue のタイトルに揃える
- **本文**: 以下を含める

```markdown
## 概要
（何をしたか、なぜその方針にしたか）

Closes #<issue番号>

## 受け入れ条件
（Issue の DoD を転記し、満たしたものにチェックを入れる）
- [x] ...
- [x] ...

## スタック
- base: `main` または `feat/1-...`（PR #29）
- ※ この PR は #29 のマージ後にレビューしてください（スタックしている場合のみ）

## 依存の追加
（追加した場合のみ。パッケージ名・バージョン・公開日・確認結果）
```

**自分でマージしない。** レビューはマージの前提。

## 7. CI の待機

PR 作成後、CI の完了を待つ。

- 確認間隔: 30秒
- **待機上限: 5分**

### CI が green の場合

正常終了。8 へ進む。

### CI が red の場合

失敗内容を確認して修正する。修正試行は **2回まで**（5 のローカル検証で使った回数と
通算する）。上限に達したら停止テンプレートで報告して終了する。

### 5分でタイムアウトした場合

待機を打ち切り、「CI が5分以内に完了しなかった」ことを報告して終了する。
それ以上ポーリングしない。CI の状態は後から `loop-status` で確認できる。

## 8. 報告

以下を出力して終了する。

```
Issue #<番号> <タイトル> を実装しました。

PR: #<PR番号>（base: <base ブランチ>）
CI: ✅ green / ⏱ タイムアウト / ❌ red

スタック:
  main
   └─ PR#29 (Issue #1)
       └─ PR#30 (Issue #2) ← 今回

次の候補: Issue #<番号> <タイトル>
（レビューとマージのあと、再度 /loop-run を実行してください）
```

**次の Issue には自動で進まない。** ここで終了する。

## 停止するとき

以下のいずれかに該当したら、その時点で停止して報告する。

- 修正試行が2回に達した
- 修正しても同じエラーが2回連続で再発した
- Issue の仕様に矛盾がある、または DoD が実現不能と判明した（試行0回で即停止）
- スタックが5段に達している
- 作業ツリーに想定外の未コミット変更がある
- スタック追従のコンフリクトを解決できない

停止時の手順は `CLAUDE.md` の「失敗時の停止ルール」に従う。要点は3つ。

1. その時点までの変更をコミットして push する（捨てない）
2. 対象 Issue に停止テンプレートでコメントする
3. 次の Issue に進まず終了する
